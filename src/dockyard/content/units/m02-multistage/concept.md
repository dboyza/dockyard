## Keep build tools out of the running application

Building software can need tools and temporary files that the running application does not need.
A **multi-stage Dockerfile** gives those two jobs separate starting filesystems.
Each `FROM` begins a new stage.
You choose which files to copy from an earlier stage into the final one.

```figure
multi-stage-build
```

For Dispatch, the first stage checks the Python file for syntax errors.
The final stage needs `app.py` and `VERSION`, but not the checking directory or generated bytecode.
This small example teaches the same separation used for applications with compilers and large build dependencies.

## Name a stage, then copy a selected file

Here is a fragment showing the two operations you’ll need:

```dockerfile
FROM ${BASE_IMAGE} AS verify
WORKDIR /source
COPY app.py VERSION ./
RUN python -m py_compile app.py
```

Keep `ARG BASE_IMAGE` before the first `FROM`, as in the previous lesson.
`AS verify` gives this stage a name that a later stage can refer to.
`python -m py_compile app.py` checks whether Python can compile the file; it does not start the API or prove all its behavior is correct.

After a second `FROM ${BASE_IMAGE}`, use a new working directory such as `/app`.
A copy instruction can select a file from the earlier stage:

```dockerfile
COPY --from=verify --chown=10001:10001 /source/app.py /app/app.py
```

`--from=verify` reads from that stage instead of your local build context.
`--chown=10001:10001` sets the file’s numeric user and group owners.
Your task also needs `VERSION`; copy it deliberately rather than bringing the whole `/source` directory into the runtime.

## Run with a user that has only the access it needs

**UID** and **GID** are numeric user and group IDs.
UID 0 is root, which has more authority inside the container than this API needs.
`USER 10001:10001` tells Docker to use that non-root identity when starting the final image’s command.
Put it in the final stage; setting it only in an earlier stage does not carry it forward automatically.

This supplied application needs to read its code and listen on port 8080.
It does not need to install packages or rewrite its source at startup.
Some applications need an entry in `/etc/passwd` for their user name, but this one works with a numeric identity.

Build and run with the commands you used in the previous image lesson.
Keep the assigned image tag, container name, ownership label, and local port mapping.
Do not mount your source folder into this container.

## Check the image you actually ran

```sh
docker exec "$DOCKYARD_CONTAINER" python -c 'import os; print(os.getuid())'
docker exec "$DOCKYARD_CONTAINER" python -c 'from pathlib import Path; print(Path("/source").exists())'
curl --fail "http://127.0.0.1:$DOCKYARD_PORT/healthz"
```

`docker exec` runs a command inside the existing container.
The first result should be a nonzero user ID, the second should be `False`, and the request should succeed.
These observations check the running container, which matters if an older container still exists after your build.

A final image can have the right files without proving that you used two stages or ran the compile step.
Review those parts of the Dockerfile yourself and explain why each stage exists.
